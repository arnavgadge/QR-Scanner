# Production readiness — Serial Scanning & Label System

Status as of Phase 11. This document states what was **actually verified, and where**. Anything tested only
against the Firebase **emulator** or a desktop browser is labelled as such; nothing here claims real-printer,
real-phone-camera or real-production-Firebase results that were not obtained.

Legend: **VERIFIED (emulator/browser)** · **VERIFIED (static/unit)** · **REQUIRES PRODUCTION FIREBASE** ·
**REQUIRES FACTORY HARDWARE**.

---

## 1. Architecture

- React 19 + Vite + TypeScript SPA (static files; no server of our own). Tailwind for styling.
- Firebase **Authentication** (email/password) and **Cloud Firestore**. All authorization is enforced by
  `apps/web/firestore.rules`; route guards in the UI are convenience only.
- Layering: UI components → hooks → services. Components contain no Firestore queries. One verification call
  site (`verifyAndRegisterSerial` in `useScanFlow`) serves manual **and** OCR entry. `window.print()` is only in
  `services/printing/printService.ts`; barcode/QR libraries only in `services/printing/codeGenerator.ts`.
- Collections: `users`, `companies`, `serials` (document ID **is** the serial → global uniqueness),
  `scan_log` (append-only audit trail), `import_history`, `export_history`.

## 2. Firebase configuration

Set at **build time** (Vite env) — see `.env.example`:

`VITE_FIREBASE_API_KEY`, `_AUTH_DOMAIN`, `_PROJECT_ID`, `_STORAGE_BUCKET`, `_MESSAGING_SENDER_ID`, `_APP_ID`.
These identify the project; they are not secrets. Access is controlled by Auth + rules.

Optional label settings: `VITE_LABEL_WIDTH_MM`, `VITE_LABEL_HEIGHT_MM`, `VITE_LABEL_DPI`
(defaults 70 × 35 mm, 203 dpi — **development values**, see `docs/PRINT_CALIBRATION.md`).

Fail-closed behaviour (VERIFIED, production-build smoke `PB9`–`PB12`):

- Missing variables → a "Firebase is not configured" screen listing them; no Firebase request is made.
- A `demo-…` project id outside emulator mode → refuses to start.
- `VITE_USE_FIREBASE_EMULATOR` and `VITE_OCR_PROVIDER=mock` are honoured **only** by the dev server; a production
  build ignores them and contains no emulator endpoints, demo config, mock OCR, seed data or test accounts
  (`npm run verify:bundle`, also run by `apps/web/tests/productionBundle.test.ts`).

## 3. Required Firestore indexes

Deploy once per Firebase project: `npx firebase deploy --only firestore:indexes --project <id>`
(**REQUIRES PRODUCTION FIREBASE**; index building can take minutes, and a filtered history query fails with a
"requires an index" error until it is READY). Definitions live in `apps/web/firestore.indexes.json`, generated by
`node apps/web/scripts/make-indexes.mjs`.

| Query (service)                                                                                                                                                                       | Needs                                                                                        | Defined?                                                         |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| Scan history with any combination of `result`, `company_id`, `source`, `scanned_by` equality filters + optional `timestamp` range, ordered by `timestamp` desc (`scanHistoryService`) | Composite `(equality fields…, timestamp DESC)` — one per non-empty subset of the four fields | **Yes — 15 indexes**; a unit test checks every subset is covered |
| Scan history with no equality filter, recent scans (`scanLogService`), export/import history (`orderBy` one field + `limit`)                                                          | Automatic single-field index                                                                 | n/a (automatic)                                                  |
| Dashboard `scan_log` `result == duplicate` + `timestamp` range (count)                                                                                                                | Served by the `(result, timestamp)` composite above                                          | Yes                                                              |
| Dashboard `serials` `scanned_at` range, `company_id ==`, `companies active ==`, `users role == & active ==` (counts)                                                                  | Single-field indexes / index merge of equality filters                                       | Automatic                                                        |
| Export `orderBy(documentId()) + limit + startAfter`; import lookup `documentId() in […30]`                                                                                            | Built-in `__name__` index                                                                    | Automatic                                                        |

No unnecessary indexes were added.

## 4. Security model (`apps/web/firestore.rules`) — VERIFIED (emulator rules engine; 64 rule tests)

Default deny; no `allow … if true`. Role/active come from `users/{uid}` (an active profile is required for every
operation).

- **Unauthenticated / no profile / inactive:** no access to app data (an inactive user may read only their own
  profile, so the app can say why).
- **Operator:** read active companies; `get` one serial (no list); read `scan_log`; **create** a serial plus its
  matching `scan_log` entry in one commit (own UID and stored name, server timestamp, active company with matching
  name, `manual`/`scan` source, serial ID == field, ≤ 100 chars). Cannot update/delete serials or logs, edit
  companies or users, create profiles, or touch import/export history.
- **Admin:** all of the above plus: list serials, create excel-source serials (create-only), validated and
  attributed company create/update (never delete), change **another** user's role/active (attributed; never
  their own; never delete), append import/export history. Never update/delete serials or `scan_log`; cannot forge
  history (a `new` log needs its serial).
- Server-generated values (`scanned_at`, `timestamp`, `imported_at`, `exported_at`, `updated_at`) must equal
  `request.time`.
- Direct-access tests (no UI) cover: self-created admin profiles, default-deny on unknown collections, mixed
  batches (all-or-nothing), deactivated company, mid-session deactivation/demotion, 100/101-character serials.

## 5. Authentication model

- Email/password sign-in; session persists (IndexedDB) across reloads; log out clears it. Signed-out users are
  redirected to `/login` for every protected route. VERIFIED (emulator/browser, `AU11`–`AU15`).
- The signed-in user's profile is a **live subscription**: an admin deactivating or demoting someone takes
  effect in that person's open session within seconds (inactive screen / "Access denied") — VERIFIED
  (`AU2`, `AU6`, `AU8`). Security never depends on this: the rules re-check the profile on every read/write
  (`AU3`, `AU9`).
- **Known limitation:** `active = false` blocks all application data but does **not** disable the Firebase
  Authentication account (needs the Firebase console or Admin SDK / a Cloud Function). A deactivated person can
  still sign in and sees only an "account inactive" screen (`AU4`). Disable the account in the console as well if
  full lock-out is required.
- **Last-admin protection:** the rules forbid changing your own role/active, so every change to an admin is made
  by a different, still-active admin; the UI also refuses to demote/deactivate the last active admin.
  Concurrent mutual demotion (2 and 3 admins, 50 rounds) never left zero admins in the emulator.
  **Not proven for production Firestore** (REQUIRES PRODUCTION FIREBASE): rule `get()` lookups are consistent with
  the write in the emulator; confirm in the pilot and keep a second admin plus console access as the recovery path
  (§14).
- Real token expiry/refresh was not tested (REQUIRES PRODUCTION FIREBASE); logout and deactivation were used as
  stand-ins.

## 6. Serial validation (one shared rule set)

`services/serial/serialValidation.ts` is the single source for value rules, used by manual entry, confirmed OCR
entry (same `verifySerial`) and **Excel import**:

- non-empty after trim/upper-case; **≤ 100 characters** (matches the `scan_log` rule);
- storable as a Firestore document ID (no `/`, `.`, `..`, `__…__`, ≤ 1,500 bytes).

Additionally, for **manual/OCR** registration only (`serialFormat.ts`): company serial format; and what the
company's **label** can encode — barcode ≤ 80 printable-ASCII characters, QR ≤ 300 — so a serial is never
registered if its label is guaranteed to fail. Excel import does **not** apply the label limits because an import
produces no label (imported serials are never printed; a duplicate scan never prints). Tests:
`serialValidation.test.ts`, `stress.test.ts`, `importClassify.test.ts`.

Leading zeros and case: stored exactly (upper-cased); `00012345` ≠ `12345`.

## 7. Excel import / export

- Import is **additive and idempotent**: parsed locally; each unique serial compared with Firestore by direct
  document-ID lookups (30 per query, never a full read); preview first; confirm creates only NEW rows in
  25-row transactions that re-read every serial (a serial registered after the preview is skipped or flagged, never
  overwritten). Invalid rows (including > 100 characters) are shown in the preview and never written.
- A failure part-way is reported honestly (`status: failed`, created / not-processed counts, history entry
  "failed"); chunks that succeeded stay, the failed chunk rolls back atomically; re-importing the same file
  creates only the missing rows (`importPartial.test.ts`). No success is shown unless the writes committed.
- Export reads the full `serials` collection in ID-ordered pages (admin only), serials stored as text, timestamps
  labelled **UTC**.
- **Large files (investigated, emulator):** 500, 1,000, 2,000 and 3,000-row imports and every export completed
  correctly with exact counts (3,000 rows written in ~26 s, export of 6,500 rows in ~7 s). Previews slowed as the
  collection grew (1,000 existing rows re-previewed in 21 s; 2,000 in 118 s; the 3,000-row preview took 173 s on
  ~3,500 documents, and a 3,000-row re-preview and a 5,000-row preview on ~6,500 documents did not finish within my
  240 s observation limit — slow, not hung: requests kept completing). Preview time is dominated by the emulator, whose `documentId() in […]` query cost grows with
  collection size (measured: 3.3 s per 30-ID lookup at 6,500 documents versus 19 ms for 30 direct gets).
  The earlier ~180 s "stall" was this slowness (requests were still completing; the UI shows
  "Checking X / N"), not a hang. Production Firestore answers these lookups from its built-in document-ID index,
  so cost is independent of collection size — **confirm with a 3,000-row import against production** during the
  pilot (REQUIRES PRODUCTION FIREBASE). No timeout was added.

## 8. OCR architecture

Provider-independent `OCRService` (Tesseract.js, self-hosted worker/data, runs in the browser, photos never
leave the device and are not stored). OCR only produces a reading; the operator must press Confirm; the confirmed
value goes through the same verification as manual entry. Medium/low/unknown confidence needs an explicit
check. Format feedback follows the **currently selected** company. Real-world accuracy is **not validated** —
use `docs/OCR_TEST_PROTOCOL.md` (REQUIRES FACTORY HARDWARE / real photos).

## 9. Barcode / QR behaviour

The company's `code_type` decides the label; operators cannot choose. Verified in the browser by decoding the
rendered code (ZXing for Code 128, jsQR for QR): value == serial exactly (leading zeros, hyphen/underscore, long
serials), no stale code after switching companies, no label for duplicates. **Physical scanning of printed
labels is pending** (REQUIRES FACTORY HARDWARE).

## 10. Printing architecture

Browser printing only (no print agent): a hidden print copy of the label is rendered at the real size; print CSS
hides everything else while `body.label-printing`; `@page` size comes from the label configuration. The browser
cannot report that a label physically printed, so the UI only says "print dialog requested". Print Again never
creates a record. **Nothing about physical printing is verified** (REQUIRES FACTORY HARDWARE) — follow
`docs/PRINT_CALIBRATION.md`. Known: a 40-character Code 128 prints at 1 dot/module (≈ 0.125 mm) on the 70 mm
development label.

## 11. Environment configuration

- Dev: `.env.local` with `VITE_USE_FIREBASE_EMULATOR=true`, `npm run emulators`, `npm run seed:dev`
  (seed script uses the Admin SDK against the emulators only and is not part of the bundle).
- Production build: `npm run build` with the six Firebase variables set; see §2. `.env*` (except
  `.env.example`) are git-ignored; no credentials are in the repository.

## 12. Known limitations

1. Real printer, label stock and physical scan distance untested; label size is a development value.
2. Real phone camera and real engraved-part OCR accuracy untested (no accuracy figures exist).
3. Real production Firebase untested (token expiry, rule-lookup consistency under real concurrency, index
   build, large-import timing).
4. Deactivating a user does not disable their Firebase sign-in (§5).
5. `scan_log` is readable by every active user (the shared Recent scans list needs it); the admin history UI is
   admin-only.
6. The admin lock-out race is verified in the emulator only.
7. Emulator-only slowness for very large imports (§7).
8. `scan_log` timestamps shown immediately after a scan fall back to the device clock for _display_ if the
   server value cannot be read back; the stored value is always the server time.

## 13. Manual production validation checklist (first deployment, before the pilot)

- [ ] Create the production Firebase project; enable Email/Password; set authorized domain.
- [ ] Deploy `apps/web/firestore.rules` and `apps/web/firestore.indexes.json`; wait for all indexes READY.
- [ ] Create the first admin in the console (Auth user + `users/{uid}` with `role: admin, active: true`);
      create a **second** admin.
- [ ] Build with production variables; confirm `npm run verify:bundle` passes and the site shows no emulator
      traffic (browser network tab).
- [ ] Sign in as admin: dashboard loads (counts), Companies page, create the real companies.
- [ ] Operator account: sign in, register a serial, repeat it (DUPLICATE), confirm Recent scans.
- [ ] Two operators on two devices submit the same new serial simultaneously → exactly one NEW.
- [ ] Admin history with every filter combination (no "requires an index" error).
- [ ] Import a 3,000-row file; time it; re-import (0 new); export; compare counts.
- [ ] Deactivate a test operator while signed in → their session shows "inactive" within seconds; also disable
      their Auth account in the console.
- [ ] Try demoting the only admin / self-demotion → refused.
- [ ] Complete `docs/PRINT_CALIBRATION.md` and `docs/OCR_TEST_PROTOCOL.md` on site.

## 14. Rollback / recovery

Data model is append-only by design: serials and scan logs cannot be edited or deleted from the app.

- **Bad import:** nothing is overwritten and nothing is deleted. Recovery is _corrective_: fix the source file and
  re-import (idempotent); wrong records created by an import are identifiable by `source: "excel"`, importer and
  timestamp (see `import_history`), and are removed/corrected by an administrator in the Firebase console
  (deliberately not possible from the app). Export first as a backup.
- **Bad company configuration:** edit the company again; stored serials/logs are unaffected.
- **Wrong role/deactivation:** another admin reverses it; if no admin can sign in, use the console to set
  `users/{uid}.role/active`.
- **Backups:** enable scheduled Firestore exports/PITR on the production project (REQUIRES PRODUCTION FIREBASE)
  and take an Excel export before bulk operations.
- **Application rollback:** the app is static; redeploy the previous build. Rules/indexes are versioned in git.

## 15. Items requiring physical factory validation

Printer model/DPI/driver, label stock size and gap, browser print scaling and margins, barcode and QR scan
distance with the real scanner(s), human-readable text size, phone camera capture of engraved serials and the
OCR accuracy that results, long-serial barcode density, mobile browsers in use on the shop floor.
